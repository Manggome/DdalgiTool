# 딸기툴 스킬 구조와 로딩 방식

## 구조

```
src/skills/
├── design-doc/     기획서 (구글 독스) — 질의응답·수정·예외처리 검수·신규 작성
├── data-table/     데이터 테이블 (구글 시트) — 조회·수정·오류 검수·신규 작성
├── balance/        밸런스 — 시뮬레이션 코드 생성·실행으로 수치 검증, HTML 시뮬레이터
├── explore/        탐색 — 소스 횡단 검색, 변경 영향도 분석, 테이블↔코드 정합성 검사
├── qa/             QA — 트렐로 카드 기반 테스트 케이스 작성, P0~P3 분류
└── archive/        아카이빙 — ADR 기록, 작업 로그(jsonl), 슬랙 90일 대비 백업
    각 폴더:
    ├── SKILL.md          짧은 본체 (트리거 + 절대 규칙 + 절차 요약, ~60줄)
    └── references/*.md   상세 절차·체크리스트·템플릿 (필요할 때만 로드)
```

## 로딩 방식 (Progressive Disclosure)

토큰 절약이 이 툴의 핵심 설계 목표이며, 스킬은 3단계로 노출된다.

1. **항상 로드 — 프런트매터만**: 에이전트 시작 시 각 SKILL.md의 `name`과 `description`만 시스템 프롬프트에 포함된다. 6개 스킬 합쳐 수백 토큰 수준. `description`은 "어떤 요청일 때 발동하는가"를 구체적 예시 문장으로 담아 라우팅 정확도를 책임진다.
2. **발동 시 로드 — SKILL.md 본문**: 사용자 요청이 description과 매칭되면 해당 스킬의 SKILL.md 전체를 읽는다. 본문은 절대 규칙과 절차 요약만 담고, 상세는 references/ 파일 경로로 가리킨다.
3. **필요 시 로드 — references/**: 실제로 그 작업 단계에 들어갈 때만 해당 reference 파일을 읽는다. 예: 기획서 질의응답에는 `design-doc/references/exception-review.md`를 로드하지 않는다.

## 공통 규칙 (모든 스킬에 반영되어 있음)

- **분류 → 표적 조회**: 인덱스 카탈로그와 project.yaml로 후보를 먼저 좁히고 필요한 것만 조회. 전체 스캔 금지.
- **쓰기는 미리보기 → 승인**: 독스/시트/트렐로/슬랙 등 외부 쓰기는 반드시 변경 내용을 보여주고 명시적 승인 후 실행.
- **출처 명시**: 모든 답변에 문서명·시트 범위·파일:라인·링크 등 근거 출처 표기.
- **대량 읽기는 서브에이전트 격리**: 긴 문서·다수 파일·스레드 통독은 서브에이전트에 맡기고 요약+인용만 메인 컨텍스트로 가져온다.
- **계산은 코드로**: 수치 계산·대량 데이터 검사는 LLM이 직접 하지 않고 스크립트를 실행한다 (balance·data-table·explore 공통).
- **작업 로그**: 모든 쓰기 작업은 `archive/logs/*.jsonl`에 1줄 기록 (스키마는 archive 스킬 참조).

## 스킬 간 연계

- 스킬은 서로의 절차를 재사용한다: qa는 design-doc의 예외처리 체크리스트를, balance는 data-table의 조회 규칙을, 모든 쓰기는 archive의 로그 스키마를 따른다.
- 경계 원칙: **검수·분석 스킬은 직접 수정하지 않는다.** 수정은 언제나 해당 소스 담당 스킬(design-doc/data-table)의 미리보기→승인 절차로 넘긴다.

## 설정

모든 스킬은 `.ddalgi/project.yaml`을 소스 위치·매핑 선언의 진실로 삼는다. 스키마 예시는 `docs/project.yaml.example` 참조.
