# 프로젝트 진단 (insight)

현재 프로젝트를 **게임 기획 관점**에서 진단해 문제점(내부 근거)과 개선점(최신 트렌드 리서치)을 담은 HTML 보고서를 만든다.

## 절대 규칙
1. **범위는 게임 기획만**: 핵심 루프·경제 순환·온보딩/초반 흐름·리텐션 장치·콘텐츠 구성과 소모 속도·과금 설계·UX 흐름.
   코드 구조·아트 퀄리티·기술 부채는 다루지 않는다 (심각한 것을 발견해도 보고서 말미 각주 한 줄로만).
2. **문제점은 내부 근거로만**: 기획서(독스/슬라이드)·데이터 테이블·아카이브 미결사항·슬랙 논의·트렐로 카드에서
   근거를 인용한다. 근거 없는 문제 제기 금지 — 근거를 못 찾으면 문제로 쓰지 않는다.
3. **개선점은 최신 웹 리서치 기반**: WebSearch 를 **오늘 날짜 기준 최근 자료 위주**로 돌린다
   (검색어에 현재 연도, "2026", "최근", 최신 기간을 포함). 같은 장르의 최근 흥행작·신작 3~5개와
   업계 아티클/포스트모템 2~4개를 조사하고, **모든 제안에 출처(게임명 또는 아티클 링크 + 게시 날짜)**를 단다.
   1년 넘은 자료뿐이면 "최신 자료 부족"을 명시한다. 유행이라고 다 넣지 않는다 — 이 게임의 루프에 붙는 것만.
4. **수치 주장은 출처 필수**: 리텐션 %·매출 등은 출처 없이 쓰지 않는다. 추정이면 [추정] 표기.
5. **산출물은 HTML 보고서**: `진단보고서_<프로젝트>_<YYMMDD>.html` 로 작업 폴더에 저장(패널 자동 표시).
   형식은 `references/report-format.md`. 채팅에는 핵심 요약 5줄 + "검토 후 슬랙에 올릴까요?" 만 (QA 스킬과 동일 — 같은 턴 업로드 금지).

## 절차
1. **프로젝트 파악**: 카탈로그 → 장르·핵심 루프·현재 시스템 목록을 잡는다. 대표 기획서 1~2개와
   구성 테이블(Content_Open·Define 류)은 스키마/목차 수준으로만. 문서 통독이 필요하면 서브에이전트로 격리.
2. **내부 진단 (문제점)**: 관점별 점검 — 온보딩/초반 5분, 경제(재화 소스·싱크 균형), 리텐션 장치(복귀 이유),
   콘텐츠 소모 속도, 과금 구조, 시스템 간 연결 공백, 아카이브의 미결 사안. 문제마다 근거 인용 + 유저 영향 + 심각도(상/중/하).
3. **외부 리서치 (개선점)**: 장르·플랫폼 키워드로 (a) 최근 흥행/신작 사례 (b) 업계 분석 아티클을 조사.
   각 개선안은 "무엇을 / 왜 (트렌드 근거+출처·날짜) / 우리 게임에 붙는 형태 / 기대 효과 / 작업량(상중하)" 구조로.
4. **보고서 생성** → 채팅 요약 → 슬랙 게시 여부 질문 후 대기.

보고서 형식: `references/report-format.md`
