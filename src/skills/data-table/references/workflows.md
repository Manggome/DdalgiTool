# 데이터 테이블 작업 상세 절차

## (a) 읽고 답변

1. **시트 특정**: 인덱스 카탈로그에서 시트/탭 후보를 좁힌다. 모호하면 후보 목록을 제시하고 확인받는다.
2. **스키마 조회**: 헤더 행(1행, 헤더가 여러 행이면 그 범위)과 전체 행 수만 먼저 가져온다.
3. **행 쿼리**: 질문 조건에 맞는 범위만 조회한다.
   - ID/이름으로 특정 행: 해당 키 컬럼만 먼저 읽어 행 번호를 찾고, 그 행만 읽는다.
   - 조건 필터/집계: 필요한 컬럼들만 통째로 받아 스크래치패드에서 스크립트로 필터·집계한다. 원본 행 덤프를 컨텍스트에 올리지 않는다.
4. **답변**: 결과 + 출처(`시트명 > 탭명 ! 범위`). 값이 비어있거나 이상하면 그대로 보고하고 추측으로 채우지 않는다.

### 서브에이전트 격리 기준
- 여러 시트를 가로질러 뒤져야 하거나, 어떤 시트에 있는지 불명확해 목록 순회가 필요할 때.
- 서브에이전트에게 "찾은 값 + 정확한 출처 범위"만 반환하게 한다.

## (b) 수정

1. 변경 대상 셀의 **현재 값을 반드시 조회**한다 (카탈로그 캐시를 믿지 않는다).
2. 미리보기 표 출력:

   ```
   시트: <시트명> > <탭명>
   | 위치 | 컬럼 | 변경 전 | 변경 후 |
   |------|------|---------|---------|
   | B15  | Hp   | 100     | 120     |
   ```

3. 명시적 승인 후 쓰기 실행. 승인 전 쓰기 금지.
4. 반영 후 해당 범위를 재조회해 값이 맞는지 확인하고 보고한다.
5. 작업 로그에 기록 (시트 ID, 범위, 전/후 값).

### 행 추가/삭제
- 행 추가: 신규 ID가 기존 ID 규칙(prefix, 증가폭)을 따르는지 확인하고 미리보기에 전체 행을 보여준다.
- 행 삭제: 삭제 전 반드시 참조 검사(다른 테이블·코드에서 이 ID를 참조하는지)를 실행하거나, 못 하는 경우 위험을 명시하고 확인받는다.

## (c) 오류 검수

`references/validation.md` 참조. 원칙: 데이터를 CSV로 export → 스크래치패드에서 스크립트 검사 → 위반 행만 리포트.

## (d) 기획서 기반 새 테이블 작성

1. **근거 확보**: 대상 기획서의 관련 섹션을 읽는다 (design-doc 스킬 절차 준용, 인용 확보).
2. **스키마 제안**: 컬럼 정의표(컬럼명, 타입, 설명, 예시값, 제약)를 먼저 제시하고 승인받는다.
   - 기존 유사 테이블이 있으면 그 명명 규칙(PascalCase 등, ID 체계)을 따른다. 카탈로그에서 유사 테이블 헤더만 조회해 확인.
3. **데이터 채움**: 기획서에 명시된 값만 넣는다. 기획서에 없는 수치는 비워두거나 `TBD`로 표기 — 임의 수치 생성 금지 (밸런스 산출이 필요하면 balance 스킬 안내).
4. **미리보기**: 생성될 테이블 전체(행이 많으면 앞 10행 + 행 수)를 표로 보여주고, 생성 위치·시트명 승인.
5. 생성 후 링크 보고, 작업 로그 기록. project.yaml의 `table_code_mappings`에 추가할 것을 제안한다(코드 연동 대상인 경우).
