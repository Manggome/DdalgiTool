# ✅ QA 하기 (qa)

무엇을 QA할지 정하고, 근거 있는 테스트 케이스를 만들고, 원하면 **유니티 에디터에서 직접 플레이하며** 테스트한 뒤
통과/실패·스크린샷·콘솔 오류를 담은 보고서를 낸다.

## 언제 쓰나
기능·카드 단위 QA 케이스 작성, 예외 케이스 검토, 유니티에서 실제 동작 확인.

## 꼭 지킬 규칙
1. **유저 행동으로 쓴다**: "부스터 아이템을 탭한다 → 즉시 발동되고 HUD 에 타이머가 보인다" ⭕ /
   "Item_Data type=7 검증" ❌. 테이블 행·코드 라인 같은 기술 근거는 `<details>` 로 접는다.
2. **케이스마다 근거**: 기획서 인용 / 테이블 행 / 코드 파일:라인 중 하나 이상. 없으면 `[추정]` 으로 분리.
3. **기대 결과를 못 정하면 기획 공백**: 기획서가 정하지 않은 상황은 케이스가 아니라 "기획 공백" 섹션으로.
4. **유니티 실행은 사용자 확인 후**: 플레이 테스트 전에 "지금 유니티를 QA에 써도 될까요?" 묻는다
   (사용자가 유니티로 작업 중일 수 있다). 앱도 대화당 한 번 승인 카드를 띄운다.

## 절차
1. **대상 정하기** — 비었으면 트렐로 "개발 끝/QA 대기" 카드나 최근 기획서를 찾아 ask_choice 로 고르게 한다.
   여러 개면 대상별로 독립 진행.
2. **근거 수집** — 대상 시스템의 기획서 섹션·테이블 스키마+대표 행·코드 분기 지점 (통독은 서브에이전트)
3. **케이스 설계** — 정상 → 경계값 → 예외 → 다른 기능과의 상호작용 순. P0~P3 우선순위.
   예외 소스로 `skills/design-doc/references/exception-review.md` 체크리스트를 재사용.
4. **어떻게 테스트할지 묻기** — ask_choice: [체크리스트만 만들기 / 유니티에서 직접 테스트 / 둘 다]
5. **(유니티 선택 시) 플레이 테스트** — `references/unity-run.md` 절차:
   unity_status → (필요 시) unity_open → unity_connect → 사용자 확인 → 플레이 →
   케이스별 조작·스크린샷·콘솔 확인 → 정지. 실제로 확인한 케이스만 통과/실패로 판정한다.
6. **보고서** — 저장 → 채팅 요약 → 슬랙 게시 여부 질문 후 대기

## 결과물
- 체크리스트: `QA_<대상>_<YYMMDD>.html` (체크박스·진행률·접이식 근거·기획 공백 섹션)
- 플레이 테스트 결과: `QA결과_<대상>_<YYMMDD>.html` (케이스별 통과/실패/확인 불가, 스크린샷, 콘솔 오류)
