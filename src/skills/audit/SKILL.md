# 🧭 어긋난 곳 점검 (audit)

기획서·데이터 테이블·유니티 코드·트렐로를 서로 대조해 어긋난 곳을 찾고, 심각도 순 보고서로 낸다.
직전 점검과 비교해 **새로 생긴 문제 / 해결된 문제**도 표시한다.

## 언제 쓰나
정기 점검, 출시·업데이트 전 확인, "기획이랑 데이터(코드) 맞아?" 같은 질문.

## 꼭 지킬 규칙
1. **결정적으로 대조**: 테이블↔코드는 project.yaml 의 `table_code_mappings` 선언대로 **스크립트**로 대조한다.
   선언 없는 매핑은 추정으로 판정하지 않는다 — 선언 추가를 제안한다.
2. **판정마다 양쪽 근거**: 어긋남 하나마다 양쪽 원문(문서 인용 / 시트!셀 / 파일:라인 / 카드)을 붙인다.
   한쪽 근거만 있으면 "확인 필요"로 분리한다.
3. **고치지 않는다**: 점검은 보고까지. 고치기는 사용자가 고른 항목만 해당 스킬(기획서·테이블)로 넘긴다.
4. **범위가 크면 나눈다**: 시스템이 여럿이면 시스템별로 서브에이전트에 맡기고 결과만 모은다.

## 절차
1. **범위 정하기** — 비었으면 전체. 설계 지도·카탈로그로 점검할 시스템 목록을 만든다.
2. **대조 4종**
   - 테이블 ↔ 코드: 매핑 선언 기반 양방향 차집합·값 비교 (`references/table-code.md`)
   - 기획서 ↔ 테이블: 기획서에 적힌 수치·목록·규칙이 테이블에 그대로 있는지 (`references/doc-table.md`)
   - 기획서 ↔ 코드: 기획서 규칙(조건·예외)이 코드 분기에 있는지 (핵심 규칙만 표본으로)
   - 트렐로 ↔ 실제: "개발 끝" 카드인데 코드·테이블에 없는 것, 반대로 반영됐는데 카드가 대기인 것
3. **심각도** — 상(유저가 바로 겪음·과금/보상 오류) / 중(일부 상황) / 하(표기·정리)
4. **직전 점검과 비교** — `.ddalgi/audit/last.json` 과 비교해 새로 생김 / 해결됨 / 그대로 표시, 이번 결과로 갱신
5. **보고서 저장** → 채팅 요약 → 고칠 항목을 ask_choice 로 고르게 하거나 슬랙 게시 여부 질문

## 결과물
`점검보고서_<범위>_<YYMMDD>.html` — 형식은 `references/report-format.md`.
비교용 `.ddalgi/audit/last.json` (항목 id·종류·심각도·근거 요약).
